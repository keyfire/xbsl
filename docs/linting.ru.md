Основной режим инструмента – проверка исходников. Полный перечень правил – отдельная страница ([Правила](/ru/RULES)); здесь – как управлять прогоном.

## Флаги CLI

`--list-rules`, `--where` (корень данных Элемента, источник и версии), `--select`/`--enable`/
`--ignore` (по id правила, группе – части id до `/` – или букве тира), `--fix`,
`--baseline`/`--write-baseline`, `--element-version`, `--data-dir`, `--lang`,
`--format text|json|codeclimate`.

`--fix` чинит механические находки прямо в файлах – хвостовые пробелы, символы типографики
(длинное тире → среднее, `…` → `...`, кудрявые кавычки и ёлочки в комментариях → прямые),
смешанные переводы строк (нормализуются к преобладающему стилю) – и отчитывается об
оставшемся. Применяются только однозначные правки и только для правил текущего прогона
(поэтому `--fix --enable typography` заодно гасит долг по тире и ёлочкам); всё, что требует
суждения, не трогается.

Для интеграции с редактором `--stdin --filename ИМЯ` проверяет один буфер из stdin (только
пофайловые правила); JSON (`{diagnostics, summary}`) – тот же, что отдаёт MCP-сервер.

`xbsl --index ПУТЬ` вместо проверки выводит в stdout JSON-индекс проекта – объекты
(с табличными частями, локальными типами модулей и семействами членов для автодополнения после
точки), объявления методов (аннотации, список параметров как написан, тип возврата и комментарий-
описание над объявлением) и именованные компоненты форм; пути POSIX относительно
корня, строки 1-based – для перехода к определению и автодополнения в редакторах.

`--format codeclimate` печатает отчёт GitLab Code Quality (issue Code Climate) с путями
относительно текущего каталога – запускайте из корня репозитория и сохраняйте вывод как
артефакт `codequality`.

## Правила подробно

**Полный перечень всех 194 правил базового набора** (severity, включённость по умолчанию,
область, ссылки на разделы документации платформы) – в
[RULES.ru.md](/ru/RULES); в рантайме –
`xbsl --list-rules`, который учитывает ещё и правила и переопределения уровней установленных
плагинов. Обзор по тирам – в README; ниже – что именно проверяют глубокие тиры.

Правило, которое судит по ЧИСЛУ, это число называет. `--list-rules` сужается так же, как набор
прогона, поэтому спросить можно про одно правило:

```sh
xbsl --list-rules --select code/duplicate-method-body
# D     code/duplicate-method-body     warning Тело метода повторяется в другом файле
#        параметр min-lines = 5 (умолчание 5, env XBSL_CODE_DUPLICATE_METHOD_BODY_MIN_LINES) - ...
```

Параметр объявлен там же, где правило им пользуется, поэтому список не может разойтись с
величиной, по которой правило судит. Любой параметр переопределяется переменной среды с именем
из `XBSL_`, идентификатора правила и имени параметра (всё, кроме букв и цифр, становится `_`).
Список печатает и действующее значение, и умолчание; неразобранное значение оставляет
умолчание и говорит об этом вслух, а прогон со сдвинутыми параметрами называет их в своей
сводке – ключ `params` в json и отдельная строка в тексте, – потому что изменённый порог
меняет находки. Инструмент MCP `list_rules(select=...)` отдаёт те же записи в `params`.

Типовые правила тира D покрывают каждую типовую позицию в коде (`новый`, приведение `как`,
аннотации, сигнатуры) и каждое значение `Тип:` в yaml (объединения `А|Б|?`, дженерики,
nullable): корень обязан быть известным типом – stdlib, объект проекта, локальный тип модуля
или глобальный тип подключённой библиотеки (см. ниже), – а цепочка с корнем-объектом проекта
не выходит за семейство порождаемых им типов:
производные из документации дистрибутива (`Ссылка`, `Объект`, `СоздатьОбъект`, автоформы...),
табличные части и структуры модулей. Квалификация через пространство имён
(`Справочник.X.Ссылка`) дополнительно сверяет вид объекта; значения перечислений проекта
проверяются и в коде, и в yaml-биндингах.

Типы подключённых библиотек линтер берёт из их архивов. `Проект.yaml` объявляет только
координаты (`Поставщик`, `Имя`, `Версия`), поэтому имена ищутся в архиве
`{Поставщик}-{Имя}-{Версия}.xlib` – в каталоге описания проекта и выше (до четырёх уровней),
то есть там, где архив и лежит при поставке исходников. Известным становится элемент с
`ОбластьВидимости: Глобально`: остальное – внутреннее дело библиотеки. Архива рядом нет –
типы библиотеки остаются неизвестными, как и до появления этой поддержки.

Межфайловые правила тира D ловят то, о чём компилятор сообщает поздно или молчит: обработчик
из yaml без метода в парном модуле, тип чужой подсистемы без секции `Импорт:`, динамический
список с типом автоформы без реквизита объекта в полях, кросс-компонентный вызов
`Компоненты.X.Метод()` без аннотации видимости, несоответствия окружений (`@НаСервере` из
клиентского обработчика без `@ДоступноСКлиента`, клиентский модуль в HttpСервисе),
зарезервированные имена (`Тип`/`type` у поля или параметра, свойство компонента с встроенным
именем), методы без единой ссылки и свойства верхнего уровня объектов по метамодели
конфигурации. Группа `query/` разбирает блоки `Запрос{ ... }` и сверяет таблицы `ИЗ`/`СОЕДИНЕНИЕ`
с объектами проекта и их табличными частями; блок с конструкциями вне поддержанного
подмножества (временные таблицы, объединения, подзапросы) пропускается целиком, а не
угадывается.

Подробные описания групп – `query/` (составной тип в `В` с подзапросом), `project/`
(свойства проекта), `naming/` (стандарт имён, extra `[morph]`) и `style/` (соглашения по
написанию кода, договорённость включено/выключено) – в
[RULES.ru.md](/ru/RULES).

## Базлайн: легаси-долг и исключения с причиной

Чтобы включить правило на коде, который его уже нарушает, и не утонуть в старых находках,
текущие находки замораживают в базлайн и спрашивают по правилу только с нового кода:

```sh
xbsl acme/app --enable style --write-baseline baseline.json   # заморозить долг один раз
xbsl acme/app --enable style --baseline baseline.json         # всплывает только НОВОЕ
```

Идентичность находки – `(файл, правило, сообщение)` с допустимым количеством: перенос строки
не будит замороженную находку, а действительно новое нарушение всплывает. Итог прогона
показывает, сколько находок погашено и сколько записей устарело (долг выплачен) – сигнал
перезаписать файл. Пути хранятся относительно файла базлайна: коммитьте его в корне
репозитория и запускайте линтер откуда угодно.

Тот же файл хранит и точечные исключения с причиной: значение записи – либо голое
количество, либо `{"count": N, "reason": "..."}`, где причина объясняет, почему код
правильный намеренно. Причины записывает действие "Исключить проверку" из лампочки
[расширения VS Code](https://github.com/keyfire/xbsl/blob/main/editors/vscode/README.ru.md#исключение-находки-базлайн) (или правка
руками); `--write-baseline` сохраняет причины выживших записей при перезаписи. LSP-сервер
принимает тот же ключ `--baseline ФАЙЛ`, поэтому исключённое гаснет и в редакторе.
В идентичность входит текст сообщения: записывайте и проверяйте базлайн под одним языком
вывода.

Устаревшими считаются только записи ТЕХ правил, которые в прогоне были. Правило, оставленное
за набором – сужением `--select`, выключенное по умолчанию, неизвестное установленной
надстройке, – находок не даёт по построению, и звать его записи устаревшими значило бы
объявить долг выплаченным, не посмотрев. Такие записи считаются отдельно ("записей базлайна
не проверено", ключ `baseline_not_checked` в json), и `--prune-baseline` их не трогает.

Устаревшие записи НАЗЫВАЮТСЯ поимённо, а не только считаются. `--stale-baseline` печатает их –
путь, правило, количество, сообщение и отдельной строкой причину записи; `--format json` несёт
те же записи в `summary.baseline_stale_entries`, и то же самое отдаёт ответ MCP `lint_paths`.
`--prune-baseline` называет их и снимает из файла, сохраняя его порядок и формат (файл лежит в
git, а перезапись с пересортировкой – нечитаемый диф), и говорит, сколько снятых записей несли
причину: после коммита их текст остаётся только в истории. Со стороны MCP то же действие
делает инструмент `baseline_prune` (с `dry_run`, чтобы сначала посмотреть); снятие никогда не
бывает побочным эффектом обычной проверки. Обычный прогон, насчитав устаревшие записи,
называет оба ключа под итоговой строкой: счёт без подсказки отправлял искать их вручную –
переписывать базлайн и сравнивать файлы.

`xbsl baseline add <пути> --rule <правило> [--reason ...]` замораживает находки по одной: гоняет
названное правило по указанным путям и дописывает только то, чего базлайн ещё не покрывает –
новый файл встаёт на своё место в порядке, остальное не двигается, записанные причины
остаются, повторный вызов ничего не меняет (`--format json` отвечает `{baseline, added,
findings, written}`). Базлайн судится только в пределах запрошенных путей: записи чужих файлов
считаются непроверенными, а не устаревшими, и `baseline_not_checked` разбит на `_rules` и
`_paths`. Сводка называет, чем судили прогон – `engine`, `plugins` с версиями, `rules {active,
total, plugin}` в json и строка "Набор прогона" в тексте, – так расхождение двух сред об одном
дереве видно сразу.

## Использование в CI

`xbsl` возвращает ненулевой код только при находке уровня **error**, поэтому командой можно
останавливать конвейер как есть – предупреждения и `info` сборку не валят. Единственное условие –
данные о языке (см. [Данные о языке](/ru/start#данные-о-языке)): сгенерируйте их в джобе (экстракторы
лежат в репозитории – чекаутьте его) либо поставьте пакет, который несёт данные через entry
point `xbsl.data` (см. [Расширение](/ru/servers#расширение-свои-правила-данные-и-уровни)), – тогда
достаточно `pip install`.

### Локально – тем же набором, что джоба

Набор правил джобы почти никогда не равен набору по умолчанию: проект включает свои правила
ключами `--enable` прямо в пайплайне. Локальный прогон о них не знает, и разницу узнаёшь из
красной джобы – круг длиной в пуш.

`--as-ci` снимает вопрос: ключи `--select`/`--ignore`/`--enable` и базлайн берутся из команды
`xbsl` в файле пайплайна рядом с проектом (`.gitlab-ci.yml` или воркфлоу GitHub; файл ищется
вверх от проверяемых путей, можно назвать явно – `--as-ci путь/к/файлу`). Совпадение получается
по построению: список правил один и тот же, второго списка, который надо держать в согласии,
не заводится.

```sh
xbsl e1c --as-ci            # набор правил как в джобе
```

Первой строкой прогон печатает, что именно взял:

```
Набор правил как в CI: /repo/.gitlab-ci.yml, джоба xbsl-lint – --enable code/unused-method, ... --baseline .xbsllint-baseline
```

Ключи складываются: `--as-ci --enable style/line-length` – это набор джобы ПЛЮС правило, которое
пробуют перед тем, как внести в пайплайн. Путь базлайна разрешается относительно файла пайплайна,
поэтому прогон из подкаталога находит тот же файл, что и джоба. Про транспорт – `--jobs`,
`--format`, пути – решает сам прогон: чаще всего проверяют одну папку, а не всё дерево.

Файла пайплайна нет или команды `xbsl` в нём нет – прогон отказывается с сообщением, а не
проверяет молча более узким набором: именно тихая разница и стоила красной джобы.

После ключа называют ФАЙЛ пайплайна, и необязательное значение – ловушка, о которой стоит
знать: в `xbsl --as-ci e1c` ключ съедает дерево, которое собирались проверить, и прогон уходит
проверять текущий каталог. Каталог, названный после ключа, отвергается с подсказкой рабочей
формы – `xbsl e1c --as-ci`, ключ после путей, – а не отказом файловой системы "это каталог".

**Пайплайн редко состоит из одного файла.** Ключ GitLab `include:` приносит джобы со стороны,
и у проекта на общем шаблоне джоба линта лежит ровно там, – читатель одного корневого файла
отвечал "команды xbsl нет" про пайплайн, который её гоняет. Локальные файлы репозитория
читаются: `include: ci/lint.yml`, `include: {local: /ci/lint.yml}`, списки того и другого и
шаблоны путей, которые разворачивает сам GitLab (`ci/*.yml`). Вложенное включение разрешается
относительно корня чекаута – так его разрешает GitLab, – а джоба, объявленная и в корневом
файле, и во включении, берётся из корневого: приоритет тот же, что у самого пайплайна. В
строке о взятом наборе называется файл, в котором команда на самом деле стоит:

```
Набор правил как в CI: /repo/.gitlab-ci.yml (включение /repo/ci/lint.yml), джоба xbsl-lint – --enable code/unused-method
```

НЕ загружается всё, что лежит вне чекаута: удалённый адрес, шаблон GitLab, файл чужого проекта,
компонент. Для этого нужна сеть, а чаще и токен, и линтер, который втихую качает адрес из
конфигурационного файла, – это неожиданность, а не удобство. Такие включения называются
(локальное включение, которого в чекауте нет, называется так же), поэтому у невидимой джобы
рядом печатается причина, а отказ выше несёт тот же перечень:

```
Включения не читались (нужна сеть или чужой репозиторий): template: Jobs/SAST.gitlab-ci.yml
```

**Какую джобу брать, когда пайплайн гоняет линтер дважды.** Проект, который собирает второе
дерево, проверяет его второй джобой – исходники одной, результат `translate` другой, – и судят
они разными наборами (у переведённого дерева нет своего базлайна и выключено правило). Без
имени берётся ПЕРВАЯ команда, и прогон вслух говорит, что выбор был:

```
Линтер в этом файле гоняет ещё: English to S3 – выбрать: --as-ci-job <имя>
```

`--as-ci-job` берёт названную (и сам включает `--as-ci`, отдельно писать его не нужно). Имя
можно назвать частью, пока подходит одна джоба, – имя с пробелами утомительно закавычивать:

```sh
xbsl build/en --as-ci-job english      # набор джобы "English to S3"
```

Часть, подходящая двум джобам, отвергается, а не угадывается; имени, которого в файле нет,
прогон отвечает списком тех, что есть.

То же доступно агенту: инструмент MCP `lint_paths` принимает `as_ci` и `as_ci_job` и кладёт в
сводку `as_ci` (файл, джоба, ключи, прочие джобы).

**И в редакторе.** Строка состояния говорит, каким набором судит панель: `CI: <джоба>`, пока
действует набор джобы, и предупреждение, когда его просили, а он НЕ взят, – сервер не
отказывается из-за отсутствующего файла пайплайна (это стоило бы всей сессии редактирования),
он продолжает судить набором настроек, и единственным следом этого была одна строка в канале
вывода. Отвечает сам сервер (запрос `xbsl/ciStatus`), а не настройки: настройки говорят, что
ПРОСИЛИ, и только сервер знает, что из этого вышло. По нажатию открывается файл пайплайна, в
котором стоит джоба.

`xbsl.linter.asCi` (и `xbsl.linter.asCiJob` для выбора джобы) заставляет
панель "Проблемы" судить тем же набором: расширение передаёт ключ, а сервер LSP читает тот же
файл пайплайна – набор правил в настройки не копируется, потому что копия и есть тот второй
список, ради отсутствия которого всё это затевалось. Собственные `xbsl.rules` редактора
остаются ПОВЕРХ набора джобы, так что пробуемое правило не теряется. Одно отличие от терминала:
если файла пайплайна нет, сервер не отказывается – отказ стоил бы терминалу одного прогона, а
редактору всей сессии, – он пишет причину в канал вывода XBSL и оставляет набор настроек.

### GitHub Actions

```yaml
lint:
  runs-on: ubuntu-latest
  steps:
    - uses: actions/checkout@v4
    - uses: actions/setup-python@v5
      with: { python-version: "3.12" }
    - run: pip install xbsl
    # генерация данных из вашего дистрибутива 1С:Элемент (или установите пакет с данными):
    - run: xbsl extract --dist "$ELEMENT_DIST"
    - run: xbsl acme/          # джоба падает при любой находке уровня error
```

### GitLab CI (виджет Code Quality)

`--format codeclimate` пишет отчёт Code Climate, который GitLab показывает прямо в merge
request. Запускайте из корня репозитория и сохраняйте вывод как отчёт `codequality`. Код
возврата при error-находках остаётся ненулевым, поэтому `artifacts.when: always` сохраняет
отчёт, даже когда джоба останавливает конвейер (нужен только виджет – добавьте `|| true`):

```yaml
lint:
  script:
    - pip install xbsl
    - xbsl --format codeclimate acme/ > gl-code-quality-report.json
  artifacts:
    when: always
    reports:
      codequality: gl-code-quality-report.json
```
