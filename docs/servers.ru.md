Движок один, а обратиться к нему можно по-разному: резидентным сервером для редактора, набором инструментов для агента, страницей в браузере. Есть и способ расширить всё это разом.

## LSP-сервер

`xbsl-lsp` из набора `[lsp]` (`pip install "xbsl[lsp]"`) запускает линтер долгоживущим
Language Server по stdio. Пофайловые диагностики он даёт на лету, при наборе, а проектные – по
сохранению. Переход к определению, автодополнение и подсказку при наведении он строит по
резидентному индексу проекта, а быстрые исправления предлагает прямо в редакторе. Платить за
старт интерпретатора на каждый вызов при этом не нужно. Ключи: `--project-root` (корень
исходников относительно папки рабочей области), `--select`/`--ignore`/`--enable`, `--data-dir`,
`--baseline`, `--templates`. Подойдёт сервер любому редактору с поддержкой LSP – VS Code,
Neovim, JetBrains.

Всё, что редактору нужно для кода, – это стандартный LSP, поэтому обычный клиент работает без
дополнительной обвязки. Сверх этого сервер отвечает на собственные запросы `xbsl/*`. На них
построены панели расширения VS Code, и по ним же эти панели можно повторить в другом редакторе:

| Группа | Запросы |
|---|---|
| Диагностики и подсказки | `xbsl/relint`, `xbsl/hoverDoc`, `xbsl/templatesReload` |
| Документация платформы | `xbsl/docsAvailable`, `xbsl/docsSearch`, `xbsl/docsPage`, `xbsl/docsTree`, `xbsl/docsAsset`, `xbsl/docsForSymbol`, `xbsl/docsByName` |
| Схемы и словари | `xbsl/uiSchema`, `xbsl/metadataSchema`, `xbsl/formKeys`, `xbsl/metaKeys`, `xbsl/metaCapabilities`, `xbsl/httpMethods` |
| Создание метаданных | `xbsl/objectInfo`, `xbsl/metaNewObject`, `xbsl/metaAddField`, `xbsl/metaSetFieldProperty`, `xbsl/metaAddForm`, `xbsl/metaAddRoute`, `xbsl/metaAddSubsystem`, `xbsl/metaAddLocalization`, `xbsl/localizationInfo` |
| Формы | `xbsl/formTree`, `xbsl/formNodeAt`, `xbsl/formEdit`, `xbsl/searchForms`, `xbsl/bindingComplete` |
| Обработчики событий | `xbsl/moduleHandlers`, `xbsl/addHandler`, `xbsl/addModuleMethod`, `xbsl/removeHandler` |

Запрос на создание метаданных возвращает план: полный текст каждого файла, который был бы
записан. Редактор применяет этот план одной отменяемой правкой, а сам сервер не пишет ничего.
CLI и MCP-сервер на том же коде пишут. `xbsl/metaCapabilities` отвечает версией сервера и
наборами видов, которые он умеет создавать: объектов, элементов разделов, форм. По ним клиент
строит меню от живого движка, а не от жёстко зашитого списка.

## MCP-сервер

Тонкий адаптер над тем же ядром. Агент – например, Claude Code – зовёт проверки как инструменты
и получает структурированные диагностики.

```sh
pip install -e ".[mcp]"
claude mcp add xbsl -- xbsl-mcp
```

Каждый пишущий инструмент `meta_*` применяет изменения и в том же ответе возвращает проверку
записанных файлов: создание и проверка за один вызов. Ядру и CLI зависимость `mcp` не нужна, она
лежит только в наборе `[mcp]`.

У каждого инструмента `meta_*` и у `lint_paths` есть параметр `root` – корень проекта
вызывающего. Агент в git worktree не делит рабочий каталог с сервером, поэтому параметр и нужен.
Относительные `directory`, `yaml_path`, `module_path`, `paths` и `baseline` считаются от него, а
ответ несёт абсолютные пути записанных файлов и находок и поле `root`, от которого их считали.
Без параметра берётся рабочий каталог сервера, как раньше. Относительный путь из рабочего дерева
тогда называет другую рабочую копию, и её чистый ответ выглядит как ваш.

**Проверка и окружение**

| Инструмент | Что делает |
|---|---|
| `lint_paths(paths, select, ignore, enable, baseline, no_baseline, root, as_ci, as_ci_job)` | проверить файлы и каталоги на диске. Относительные пути считаются от `root`, и сводка его называет. Список принятых замечаний `.xbsllint-baseline` применяется сам, как и в CLI: `summary.baselined` говорит, сколько находок погашено, `no_baseline` показывает и замороженные, а устаревшие записи названы поимённо в `summary.baseline_stale_entries`, не только сосчитаны. `enable` добавляет к умолчаниям правило, выключенное по умолчанию, – так проект спрашивает про пробелы словаря. `as_ci` берёт набор правил и список принятых из задачи конвейера проекта (`.gitlab-ci.yml` или рабочий процесс GitHub рядом с проектом): предварительная проверка тогда судит тем же, чем задача конвейера, а сводка несёт `as_ci` – файл, задачу, ключи и прочие задачи с линтером. `as_ci_job` называет, какую из них взять: конвейер, проверяющий второе дерево с переводом, запускает линтер дважды и двумя разными наборами |
| `lint_source(filename, content, select, ignore)` | проверить содержимое в памяти, до записи файла |
| `baseline_prune(paths, select, ignore, enable, baseline, dry_run, root)` | снять записи, которые этой проверке больше не нужны (ключ CLI `--prune-baseline`). Ответ называет каждую: путь, правило, сообщение, количество и причину, написанную человеком. Файл сохраняет свой порядок и формат. Записи правил, которых у сервера нет, и файлов вне `paths` не трогаются, а `dry_run` показывает, что ушло бы |
| `list_rules(select, ignore)` | доступные здесь правила: id, заголовок, тир, область, severity – и `params` у правила, которое судит по числу (действующее значение, умолчание, переменная среды для переопределения); `select` отвечает про одно правило вместо всего реестра |
| `version_info()` | чем отвечает окружение: движок, интерпретатор, версия данных, надстройки. Так различают два окружения, которые отвечают на одном файле по-разному |

**Документация платформы и схемы**

| Инструмент | Что делает |
|---|---|
| `docs_search(query, limit)` | полнотекстовый поиск по документации 1С:Элемент |
| `docs_page(id, brief, section)` | страница документации по идентификатору из двух других инструментов; `brief` – одна шапка: краткое описание и имена разделов вместо текста, `section` – шапка плюс один раздел статьи (Свойства, Методы, Конструкторы, ...; на неизвестный раздел ответ – перечень имён на выбор) |
| `docs_symbol(name, brief, section)` | документация символа по имени, в любом написании: тип отвечает своей страницей и теми же режимами `brief` и `section`, член (`Подстрока`, `Строка.Найти`) – блоком одного этого члена со склеенными перегрузками: своей страницы у члена нет. Член, объявленный несколькими типами, отвечает их именами и тем, как переспросить |
| `type_members(name)` | члены stdlib-типа одним компактным ответом – что может стоять после точки; дешевле страницы, когда нужен только список членов |
| `ui_schema(component, brief, property)` | ui-схема компонента интерфейса: палитра конструктора и типизированные свойства |
| `metadata_schema(kind, sections, names)` | какие свойства вправе объявить элемент заданного `ВидЭлемента` |

Трём инструментам `docs_*` нужна база `docs.sqlite` (см. [Поиск по документации](/ru/platform-data#поиск-по-документации)), а двум схемным – сгенерированные данные о языке. Страница типа – это тысячи знаков: конструкторы, каждое свойство, списки унаследованного. Целиком она нужна тогда, когда её собираются читать. `brief` отвечает на вопрос "что это за страница и о чём она", а `section` – на один вопрос по ней.

**Перевод исходников** (см. [Перевод проекта](/ru/translation))

| Инструмент | Что делает |
|---|---|
| `translate_status(root)` | покрытие и остаток, дешёвая проверка перед любым решением. Корень без словаря получает отказ с перечнем мест, где словарь искали |
| `translate_gaps(root, kind, filter, limit, offset, compact)` | чего словарь ещё не покрывает, страницами: частота, первые места, собственное написание платформы подсказкой; `compact` оставляет в строке только ключ, вид и частоту; в ответе – прочитанный `dictionary` |
| `translate_entries(root, kind, filter, limit, offset)` | что словарь уже говорит, с файлом и строкой каждой записи |
| `translate_unused(root, kind, filter, since, limit, offset, prune, compact)` | обратный вопрос: что словарь всё ещё говорит, а проекта уже нет. Удаление компонента навсегда оставляет за собой его имена и строки комментариев, и сказать об этом больше некому; `since` сужает ответ до сирот одной правки – ключей, встречавшихся только в строках, снятых по git diff (ветка или коммит – от точки расхождения до рабочего дерева, диапазон `A..B` – как написан); `prune` снимает ровно ту страницу, которой отвечает, и по умолчанию выключен |
| `translate_set(root, edits, edits_file, target, comment)` | запись: добавить, исправить на месте или снять, обнулив значение; `edits_file` – пачка файлом (yaml формата словаря либо список JSON), `comment` – заголовок, с которым создаётся новый файл словаря |

Все четыре отвечают страницами поверх одного ядра движка, поэтому наполнение словаря на тысячи
записей не требует вычитывать файлы.

**Проект и его объекты**

| Инструмент | Что делает |
|---|---|
| `meta_project_info(root)` | карта исходников под корнем: проекты, подсистемы, объекты по видам |
| `meta_object_info(root, name, yaml_path)` | описание одного объекта: всё, что нужно, чтобы писать его формы и код |
| `meta_new_project(...)` | создать проект: `Проект.yaml`, `Проект.xbsl` и первую подсистему |
| `meta_new_object(directory, kind, name, ...)` | создать объект: `<Имя>.yaml` и `<Имя>.xbsl` у видов с модулем |
| `meta_rename_object(..., dry_run)` | переименовать объект и обновить все ссылки в исходниках |
| `meta_delete_object(..., dry_run)` | удалить объект целиком: пару yaml/модуль и его формы |
| `meta_add_subsystem(parent_dir, name, ...)` | создать подсистему – папку с `Подсистема.yaml` |
| `meta_add_dependency(root, vendor, name, version, ...)` | подключить библиотеку – раздел `Библиотеки` в `Проект.yaml` |
| `meta_set_access(root, ..., default, permissions, calc_by)` | задать `КонтрольДоступа.Разрешения` у объекта |

**Поля, маршруты, методы, формы, локализация**

| Инструмент | Что делает |
|---|---|
| `meta_add_field(yaml_path, field_kind, name, type, props, ...)` | добавить элемент раздела: реквизит, измерение, ресурс, значение перечисления, параметр, поле, табличную часть. Стандартный реквизит (`Номер`, `Дата`, `Код`, `Наименование`, `Владелец`) судится своим классом: `Длина`, `Уникальность` и блок `Автонумерация` принимаются, а `type` можно не указывать там, где класс его задаёт. `props` принимает вложенный блок словарём или ключом через точку (`Автонумерация.Префикс`), а список – последовательностью. Блок класса, которого метамодель не описывает (`Представление`), отвергается как известное ограничение. Секция, которой в файле нет, заводится в конце файла; у регистра поле `notes` говорит об этом и называет соседний вид, который положил бы элемент рядом с существующими полями: `ресурс` там, где просили реквизит, и наоборот |
| `meta_set_field_property(yaml_path, field_kind, name, props, ...)` | задать свойства уже существующему элементу раздела; формы значений те же, что у `meta_add_field`, вложенный блок заменяется целиком |
| `meta_add_route(yaml_path, routes, template, methods)` | добавить `HttpСервис` шаблоны url и заготовки обработчиков |
| `meta_add_method(module_path, name, params, returns, ...)` | вставить метод в модуль `.xbsl`, не разрывая блоки аннотаций |
| `meta_add_form(root, ..., forms, card_min_width, card_placeholder)` | сгенерировать формы объекта и зарегистрировать их в `Интерфейс` |
| `meta_add_localization(yaml_path, language)` | добавить файл перевода элементу локализованных строк |
| `meta_set_localization(yaml_path, name, values, section)` | записать одну строку локализации во все языки сразу: текст языка по умолчанию – в сам элемент, каждый другой – в свой файл перевода; язык, о котором вызов молчит, всё равно получает строку значением языка по умолчанию и заметкой |
| `meta_localization_info(yaml_path)` | картина локализации: объявленные языки и что ещё не переведено |

**Компоненты формы – конструктор из скрипта**

| Инструмент | Что делает |
|---|---|
| `meta_component_tree(yaml_path, node_id, name, max_depth, properties, brief)` | дерево узлов компонента интерфейса; большую форму можно брать частями – поддеревом (по идентификатору узла или по его `Имя`), с пределом глубины, без записей свойств либо одним скелетом (`brief` – идентификаторы, виды, типы, имена и слоты: несколько килобайт на дерево в сотни) – большое целое дерево несёт подсказку об этих ручках |
| `meta_add_component(yaml_path, parent_id, slot, ...)` | вставить новый компонент в слот родительского узла |
| `meta_insert_fragment(yaml_path, parent_id, slot, fragment, ...)` | вставить в слот готовый блок yaml одного компонента (скопированное поддерево) |
| `meta_move_component(yaml_path, node_id, new_parent_id, slot, ...)` | перенести узел в другой (или тот же) слот; комментарии над ним едут следом |
| `meta_move_components(yaml_path, node_ids, ...)` | перенести несколько узлов одной операцией, сохранив их порядок в документе |
| `meta_remove_component(yaml_path, node_id)` | удалить узел вместе с его комментариями |
| `meta_remove_components(yaml_path, node_ids)` | удалить несколько узлов одной операцией |
| `meta_set_component_property(yaml_path, node_id, key, value, value_yaml)` | задать, заменить или удалить свойство узла |
| `meta_add_handler(yaml_path, node_id, key, method, signature)` | привязать событие узла к методу-обработчику парного модуля |

Те же операции доступны из CLI ([Команды](/ru/CLI)) и, для редактора, через LSP-запросы `xbsl/meta*`.

## Веб-интерфейс

Локальная страница: укажите папку проекта и увидите замечания. Написана она на стандартной
библиотеке, внешних зависимостей нет, и слушает она только `127.0.0.1`.

```sh
xbsl-web            # затем открыть http://127.0.0.1:8771/
```

На странице есть настройки правил по тирам, выбор версии данных, фильтры по severity и по
тексту, тёмная и светлая темы. Клик по замечанию открывает файл в VS Code (`vscode://`).

## Расширение: свои правила, данные и уровни

Три группы точек расширения (entry points) позволяют отдельному пакету дополнить линтер, не
отводя собственную его копию. Это нужно тем, чьи правила или языковые данные нельзя публиковать:
их держат в закрытом пакете, который зависит от `xbsl`.

```toml
# pyproject.toml вашего пакета
dependencies = ["xbsl>=0.16"]

[project.entry-points."xbsl.rules"]
мой-проект = "мой_проект.rules"      # импорт модуля выполняет его декораторы @rule

[project.entry-points."xbsl.data"]
мой-проект = "мой_проект:data_root"  # путь либо функция, возвращающая путь

[project.entry-points."xbsl.severity"]
мой-проект = "мой_проект:severity_overrides"   # {id правила: "error"|"warning"|"info"|"off"}
```

Пакеты, объявившие группы под старым именем (`xbsllint.rules`/`xbsllint.data`/`xbsllint.severity`),
продолжают работать: старые группы сканируются вслед за новыми.

Словарь уровней – или функция без аргументов, которая его возвращает – поднимает и понижает
уровень любого правила, встроенного или из плагина, для всех запусков этой установки. Проект
может считать, например, `style/abbreviation-case` предупреждением, пока публичное значение по
умолчанию остаётся info. `"off"` убирает правило из набора по умолчанию; явный `--select` или
`--enable` всё равно включит его, с базовым уровнем.

Пакет установлен – и CLI, и MCP-сервер, и веб-панель видят все расширения. Ключей и файлов
настройки для этого не нужно. Сбой точки расширения роняет запуск, а не ограничивается
предупреждением: линтер, молча потерявший правило, остаётся зелёным в CI и ничего не
гарантирует. Переопределение с неизвестным id правила или уровнем падает по той же причине.
`XBSL_NO_PLUGINS=1` игнорирует все внешние пакеты: остаются встроенные правила, вшитые данные и
уровни по умолчанию.
