Команда `xbsl translate` переводит исходники проекта 1С:Элемент на английские написания.
Ключевые слова, ключи метаданных, типы, члены и значения перечислений 1С:Элемента имеют русское и
английское написание. Перевод использует извлеченные [данные 1С:Элемента](platform-data) и словарь
имен проекта, который ведет команда разработки.

```sh
xbsl translate e1c/app                          # только отчёт: покрытие и что осталось
xbsl translate e1c/app --coverage               # плюс разбивка по объектам метаданных
xbsl translate e1c/app --missing gaps.yaml      # непереведённый остаток заготовкой словаря
xbsl translate e1c/app --out build            # записать переведённое дерево (в build/e1c/app)
xbsl translate e1c/app --out build --strict   # ненулевой выход, пока не полно
```

## Что чем переводится

**Встроенные имена берутся из данных 1С:Элемента.** Регистр ключевого слова сохраняется:
`Если` становится `If`, `если` становится `if`. Для ключа yaml используется английское
написание, объявленное классом метамодели. Поэтому одно слово в разных узлах может переводиться
по-разному. Значение перечисления ищется внутри своего перечисления: одному русскому значению
могут соответствовать несколько английских в разных перечислениях.

В выражениях типа сохраняются форма и фасеты: `.Ссылка` становится `.Reference`. Это действует
для yaml и кода во всех позициях, где парсер читает тип: параметр, объявление, конструктор,
приведение и аргумент типа. Слово после точки в другой позиции является членом. Для получателя
с фасетом объекта проекта или цепочки, которая загружает запись, член-ссылка также записывается
как `Reference`. Свойство-ссылка надписи или картинки записывается как `Link`. Значение свойства
с объединенным типом, совпадающее с одним из членов (`Авто` в `Авто|Число`), получает написание
из пары названий типов 1С:Элемента.

Для блоков `Запрос{ ... }` используется словарь языка запросов. Имя без соответствия в данных
остается без изменения и включается в отчет как пробел данных. Если звено цепочки объявлено как
`A|B`, определить его владельца невозможно: анализ цепочки останавливается, а следующее слово
читается без владельца. Выражения внутри интерполяции строки обрабатываются как код окружающего
метода, включая цепочки. Например, `"%{Объект.Товары.Граница()}"` обрабатывается так же, как
то же выражение вне кавычек.

**Имена проекта переводятся по словарю.** В словарь добавляют переводы имен проекта: объекты,
методы, реквизиты, компоненты форм, ключи словарей, файлы ресурсов и значение по умолчанию
перечисления – голое или квалифицированное своим перечислением, как `Состояния.Открыт` в
`States.Open`. Туда же идет каждая кириллическая строка комментария – и в модуле, и в файле
ресурсов. Планов три:

```yaml
version: 1
language: en

# tokens: идентификатор целиком -> идентификатор целиком (файл ресурса – основой имени)
tokens:
    Задачи: Tasks
    Значок: Icon

# phrases: строка комментария -> её перевод
phrases:
    "Задача помечается выполненной.": "The task is marked done."
```

Ключ фразы – одна строка комментария без маркера, отступа и экранирования. Для плана `literals`
ключ и значение записываются с экранированием исходного кода. Если ключ фразы ошибочно передан с
экранированной кавычкой, `--set` и `translate_set` нормализуют его и сообщают об изменении в
`normalized`. Пробелы по краям значения тоже удаляются: переводчик восстанавливает отступ строки.
Если значение изменилось только за счет пробелов, запись в `rewritten` получает признак
`whitespace_only`. Многострочный ключ отклоняется, потому что каждая строка комментария
переводится отдельно.

Новый файл создается с отступом в четыре пробела. При записи в существующую секцию инструмент
копирует отступ соседних записей, поэтому сохраняется и другой отступ, например в два пробела.
Это действует при правке из панели и через `--set`.

Третий план – `literals` – про строковые литералы кода:

```yaml
literals:
    "Файл не загружен": "The file was not uploaded"
    "Не заполнено поле \"Наименование\"": "The \"Name\" field is empty"
    "Не разобрано тело: %{Описание}": "Could not parse the body: %{Описание}"
```

Переводчик заменяет только литералы, перечисленные в словаре. Ключ и значение записываются так,
как текст выглядит между кавычками в исходнике, с тем же экранированием. Значение, которое не
является допустимым телом литерала, отклоняется при загрузке словаря. Интерполяция в значении
записывается как в исходнике; движок переводит имя внутри нее. Литералы внутри `Запрос{}`,
`Образец{}` и других разрешимых литералов не изменяются, поскольку содержат код.

План `literals` также применяется к двум случаям, в которых текст связан с кодом:

- **Имя именованной группы** образца, `(?<Имя>...)`. Код обращается к группе по этому имени,
  например через `Группа("Имя")`. Имя группы и аргумент вызова переводятся из одного источника:
  сначала по плану литералов, затем обычным разрешением имени. Это сохраняет соответствие между
  объявлением группы и обращением к ней.
- **Шаблон представления** вида события журнала. Выражения внутри шаблона переводятся как имена,
  а текст – по записи плана литералов для всего значения. Если записи нет, текст включается в
  отчет пропусков.

Суффиксы литерала длительности в коде переезжают на английские написания сами: `300мс`
становится `300ms`, а `2д14ч30м5с6мс` – `2d14h30m5s6ms`. Состав русских суффиксов задан справкой
типа, английский подтвержден компилятором 1С:Элемента. Число, склеенное с любыми другими буквами,
не трогается.

Тем же планом идет всякое значение yaml, которое метамодель объявляет локализуемым текстом
(`Localizable`), – всякое, а не одни представления команд. `Представление` – такое свойство у
полусотни классов: у справочника и документа, у реквизита, измерения и ресурса, у команды, у права
доступа, у значения перечисления. Рядом с ним стоят заголовки приложения (`ЗаголовкиПриложения`),
сообщения, которыми приложение просит у пользователя разрешение
(`СообщенияЗапросаРазрешений`), представления групп справочника
(`ПредставлениеГруппыСправочника`), `ПредставлениеАктивного` и `ПредставлениеНеактивного` у
переключаемой команды, а также шаблоны представления события журнала – `ШаблонПредставления` и
соседние `ШаблонПредставленияНачала`, `ШаблонПредставленияКонца`, `ШаблонПредставленияОшибки`.
Каждый такой текст человек читает на странице, поэтому он либо назван записью целиком, либо
предъявлен пропуском. Исключение – свойство `Описание`: это документация разработчика, она
остается данными. Только описание с подстановкой `%{...}` идет через план так же, как шаблон, и
тогда его пропуск попадает в список.

Пропуск в любом из этих текстов роняет `--strict`: английская сборка показала бы его по-русски.
Остальные пропуски плана попадают в список и проверку не роняют: строковый литерал модуля или
выражения с `=`, текст с `%{...}` в дереве компонентов, описание. Отличить там данные от сообщения
может только сам проект. Значение с `=` – это код, поэтому ключом его строки служит текст между ее
собственными кавычками, как в модуле.

Пометку устаревшего элемента движок переводит сам. Стандарт имен начинает заголовок такого
элемента с `(не используется)`, а `naming/presentation` требует от английского проекта
`(not used)`, поэтому в английском дереве на этом месте стоит английская пометка. Если пара
словаря пометку опускает, переводчик ставит ее перед текстом пары. У текста без пары меняется
только пометка, и он остается пропуском. Так же меняется пометка в представлении отчета, которое
переводчик оставляет данными. Пару, которая начинается со своей скобки, переводчик пишет как есть,
и правило укажет на нее в английском дереве.

Префикс имени устаревшего элемента движок тоже переводит сам. Стандарт начинает такое имя с
`Устарело`, а в файле английского дерева от русского имени больше ничего не остается: устаревший
элемент правило распознает там только по префиксу `Deprecated`. Поэтому переводчик сохраняет префикс,
что бы ни написала пара. Пару, которая начинается с `Deprecated`, он пишет как есть, а любой другой
ставит префикс спереди: из `УстарелоКурсы: Rates` и `УстарелоКурсы: ObsoleteRates` выходят
`DeprecatedRates` и `DeprecatedObsoleteRates`. За именем идут файл элемента и все обращения к нему.
Имя, которое только начинается с тех же букв, как длинное слово, остается таким, как в паре.

Текст, который должен читаться одинаково на обоих языках – название продукта, код, слово, которое
английский взял целиком, – называют записью, повторяющей ключ значением:

```yaml
literals:
    "Цена товара": "Цена товара"
```

Проход вернет текст как был, план сочтет его названным, и `--strict` не найдет, о чем сообщить.
Такую пару не трогают ни `--unused`, ни `--redundant`: проход ею пользуется, а в данных 1С:Элемента для нее нет соответствия.

Имена переводят целиком, а не по словам. Порядок слов английского имени обратный русскому, а
части русского имени склоняются, поэтому склейка пословных переводов дает кальку. Комментарии
переводятся построчно: правка соседней строки не обесценивает запись, а одна запись обслуживает
все повторы. Готовый блок комментария переразбивается по ширине проекта – той же, которой
пользуется правило `style/line-length`. Иначе перевод, ставший длиннее исходника, вылезал бы за
предел. Так переразбиваются и строки `//` и `///`, и комментарий `/* ... */`. У такого комментария
`/*` остается в начале первой строки, а `*/` – в конце последней. Рамки и разделители, списки,
таблицы и образцы кода остаются как были. Строки, длинные уже в исходнике, – тоже.

Строка документирующего комментария, которая открывает тег, – `@параметр Коды - Коды для
проверки.` – сначала ищется в словаре целиком, и пара на всю строку по-прежнему главнее. Без нее
строка переводится по частям: слово тега становится английским (`@parameter`, `@returns`,
`@throws`, `@see`), имя после `@параметр` или `@выбрасывает` переводится так же, как в коде,
ссылка, записанная именами (`@см Модуль.Метод`), переводится как имена, и только текст после
имени – фраза, ключом которой служит сам этот текст. Параметр, переименованный в разделе
токенов, тогда меняется в теге вместе с сигнатурой, а имя без пары – такой же пробел, как то же
имя в коде. Переразбивка никогда не приклеивает тег к строке выше: среда разработки читает тег
с начала строки, поэтому тег и строки его продолжения переразбиваются отдельным абзацем.

Строку кода, которую английские имена вытолкнули за предел, переводчик переносит так, как
руководство по стилю переносит выражение: после запятой между аргументами, параметрами или
элементами коллекции, после открывающей скобки такого списка или перед операцией, которая тогда
открывает следующую строку. Места переноса берутся из дерева разбора, поэтому запятая между
аргументами типа местом переноса не становится. Продолжение сдвигается на один отступ. Строка с
комментарием после кода остается как была, как и строка, о которой `style/line-length` сообщает
уже в исходнике. Проход проверяет свой результат: токены модуля и дерево разбора не должны
измениться.

Словарь – это каталог yaml-файлов или один файл с именем `xbsl-translation`, и ищут его рядом с
проектом и выше. Чтобы наполнить словарь, кладут заполненную заготовку рядом с остальными
файлами. Два файла, разошедшиеся в одном ключе, отвергаются при загрузке, и так же отвергается один
файл, где ключ объявлен дважды с разными переводами.

Отказ называет все такие ключи разом – секцию, ключ и перевод в каждом файле, – а не первый
встреченный. Две ветки однажды закрыли одни и те же пропуски своими файлами; каждый конвейер был
зеленым, а слитый словарь не загрузился: десять ключей переведены дважды, четыре – по-разному. По
одному за раз это было четыре загрузки.

Место – это файл и строка, и ключ, повторенный внутри одного файла, – коллизия того же рода. Разбор
yaml оставляет у повторенного ключа только последнее значение и о первом ничего не сообщает, поэтому
файлы словаря читаются со строкой каждого ключа. Повтор с двумя значениями отвергается вместе с
остальными конфликтами, а повтор того же значения – лишняя копия. Один и тот же ключ в двух секциях
повтором не считается, а заголовок секции, написанный в файле дважды, читается как одна секция: так
его читает и таблица записей. Замер на живом словаре из 167 файлов: повторов внутри файла нет,
загрузка дольше не стала.

`--check-duplicates` сообщает о разных переводах одного ключа с кодом возврата 1,
об одинаковых дублях – с кодом 0. У каждого места сохраняются файл и строка.

`--against REF` сравнивает рабочий словарь и ссылку через общую базу Git.
Односторонние правки, удаления и отслеживаемые переименования не возвращают старую
копию из базы. Разные правки одного ключа и новые дубли двух веток показываются
как конфликты. Удаление против правки и неоднозначное переименование требуют
разрешения. Переименование сначала добавляют в индекс: новый неотслеживаемый
файл сам по себе его не доказывает. Несвязанная история также вызывает отказ.

`--format json` возвращает `conflicts` и `duplicates` в виде
`{section, key, places: [{file, line, value}]}`. Объект `against` содержит `ref`,
`merge_base`, `files` и `added`; последнее поле считает записи, выбранные со ссылки.
Их места помечены `REF:файл` и исходными номерами строк. Проверяются переводы ключей,
а не все конфликты Git в шапках и комментариях файлов.

Для `--strict` отдельный флаг не нужен: рабочий словарь с конфликтом не загружается.
Одинаковые дубли считаются в обычной сводке.

**Квалифицированная запись** (`Словарь.Ключ: SignIn`) действует только внутри одного пространства
имен. Ключу словаря локализованных строк может быть нужно написание, которого тому же слову нельзя
дать в коде.

Запись с именем метода действует на его локальные имена, включая параметры. Она не
переименовывает псевдонимы внутри `Запрос{...}`: псевдоним и обращение к полю результата
получают общее написание. Переменная `поймать` с аннотацией `Исключение` тоже участвует
в разрешении членов по типу. Ее свойство `Причина` получает написание `Cause` из данных 1С:Элемента,
даже если словарь задает другой перевод одноименному полю проекта.

При переносе переведенных комментариев строки с более глубоким отступом под пунктом списка
остаются отдельными. Это действует и для строчных, и для блочных комментариев. Пустая строка
комментария заканчивает продолжение списка; обычный абзац после нее снова может переноситься.

## Имена, объявленные проектом, принадлежат проекту

Имя проекта может совпадать со словом из словаря 1С:Элемента. Это может быть значение
перечисления, реквизит, метод или ключ словаря. Такие имена переводятся только по словарю проекта.
Объявление и обращения к нему получают одинаковое написание или остаются без перевода до
добавления записи в словарь. Это предотвращает несовпадение имени в yaml и обращений к нему
в модуле.

Исключение составляют встроенные элементы коллекций, различаемые по имени: стандартные код,
наименование и владелец. К исключениям также относится фасет после точки в выражении типа.

Имя переопределяемого обработчика 1С:Элемента переводится по данным технологии. Метод под `@Обработчик`, названный
как обработчик из списков 1С:Элемента, не считается именем проекта: компилятор находит
переопределение по имени 1С:Элемента. В модуле, который объявляет этот обработчик, объявление и
вызовы метода в модуле получают английское написание из списков в данных. Модуль компонента
интерфейса переопределяет то, что объявляет его база (`ПослеСоздания` – `AfterCreate`), модуль
другого элемента – то, что компилятор объявляет для его вида и модуля: `ПередЗаписью` и
`ПриСозданииНаОсновании` в модуле объекта справочника, `Обработчик` в модуле запланированного
задания, `ПроверитьНаличиеКлючейДоступа` в модуле ключа доступа, обработчики RLS вроде
`ВычислитьРазрешенияДоступаДляОбъектов` в модуле сущности. В остальных модулях имя переводит
словарь 1С:Элемента. Запись словаря проекта с другим написанием попадает в дефекты словаря, с тем же –
в лишние. Пока в данных нет списков, такое имя ждет записи в словаре, как раньше.

Имя встроенного типа распознается в местах, где может стоять только тип: в выражении типа, в корне
статического вызова и прямо перед фасетом, как в `Сущность.Право`. Поле, реквизит или метод проекта
с тем же написанием ничего там не держат. Словарем отвечает только тип, который проект объявил под
этим именем, поэтому его объявление и употребления по-прежнему переезжают вместе.

Имя в области видимости – тоже не тип. Локальная переменная, параметр, переменная цикла или
`поймать`, параметр лямбды и свойство своего элемента модуля могут писаться как встроенный тип, и
тогда `Имя.Член` сохраняет написание объявления. Типом такое слово остается в статическом методе, у
которого нет элемента, и в методе компонента, который компилируется только на сервере и имеет доступ только к контекстным свойствам. Код внутри строковой интерполяции принадлежит своему методу и видит те же
имена, типы и записи словаря.

Файл ресурса – имя проекта во всех местах, где оно стоит. Файл дерева, свойство yaml, путь в строке и
тело `Ресурс{...}` вместе получают слово словаря или вместе сохраняют собственное имя файла.

Картинки стандартной библиотеки 1С:Элемента не относятся к файлам проекта. У каждой картинки есть русское и
английское имя. Английское имя достается ссылке, которую разбирает компилятор: значению свойства
с картинкой и телу `Ресурс{...}`. Пространство имен библиотеки при этом можно и не писать:
`Стд::Аккаунт.svg` становится `Std::Account.svg`.

Имя без пространства имен сначала ищут среди файлов проекта: когда у проекта есть свой файл с тем
же именем, ссылка ведет на этот файл. Имя с пространством имен библиотеки всегда означает
библиотеку – его для того и пишут.

Строковый путь не обращается к ресурсам библиотеки. Путь в строке читает `ПакетРесурсов.Текущий()`, то есть
ресурсы своего пространства имен. Поэтому строковый литерал и значение yaml, которое схема считает
текстом, остаются как написаны, даже когда буква в букву совпадают с именем картинки.

Английские имена картинок перевод берет из раздела `resource_paths` файла `uiterms.json` в данных
1С:Элемента, и на данных без этого раздела ссылка их не получает.

Метод, объявленный компонентом проекта и вызванный через узел формы, – тоже слово проекта, а
команда встроенного компонента сохраняет написание словаря интерфейса.

## Что не трогается

Данные. Подписи, описания и любой другой текст, который читает пользователь, остаются как
написаны: их переводит штатный механизм локализации, и в переведенном проекте сохраняются те же словари.
Строковые литералы тоже остаются. Исключение – код внутри их интерполяций: он разбирается заново
и переводится как обычный код. `Ид` не меняются, потому что переведенное дерево – тот же проект,
а не его копия.

Строковый литерал, совпавший с переименованным именем, попадает в предупреждения. Вызов метода по имени из строки перестает работать без предупреждения, если переименовано только объявление.

Предупреждение `literal-data-value` относится к литералу, который совпадает со значением в
json-ресурсе проекта и изменяется записью плана `literals`. Такой литерал может использоваться
для сравнения с данными, например при разборе начального заполнения. Данные не переводятся,
поэтому после изменения литерала сравнение перестает совпадать. Чтобы оставить литерал без
изменений и учесть его в покрытии, добавить запись со значением, равным ключу. Отчет выводит
предупреждения списком с файлом, строкой, видом и текстом.

Предупреждение `short-pair` относится к короткой строке комментария. Пара фраз задается для одной
строки, но перевод одного или двух слов зависит от контекста. Например, `нет.` могли перевести
как `timer.` для конца предложения о таймере. Если комментарий содержит непереведенные строки,
а короткая строка того же комментария переведена такой парой, отчет выводит предупреждение для
короткой строки. Каждый пропуск этого комментария в `--gaps` и `translate_gaps` содержит поле
`neighbors` с короткими строками и их переводами для проверки контекста. Строки с одинаковым
маркером, записанные подряд, считаются одним комментарием; в yaml одним комментарием считается
последовательность строк комментария. Если переведены все строки, предупреждение не выдается.

Исключений два, и оба – это имя, записанное второй раз, вне кода.

**Ключи json-ресурсов проекта, называющие поле его структуры.** Структура читает json по имени
поля, поэтому такой ключ и есть то же имя, записанное еще раз. Если переименовать поле и сохранить прежний ключ, данные не свяжутся с полем: настройки чтения без предупреждения пропускают неизвестное свойство и инициализируют отсутствующее поле. Проект компилируется, применяется и стартует с пустыми данными.
Такие ключи переезжают тем же словарем, что и поля. Значения и ключи, которых не объявляет ни одна
структура, – карта по содержимому, внешний контракт – остаются как написаны. Число переименованных
ключей стоит в сводке.

**Литерал, который записывает путь к ресурсу** – например, `"Значки/%Код.svg"`. Перевод
переименовывает файлы и каталоги ресурсов, и путь обязан следовать за ними, иначе 1С:Элемент ресурс
не находит. Литералом пути считается только то, что им и выглядит: он оканчивается известным
суффиксом ресурса, а каждый сегмент читается как имя файла. Регулярное выражение с косыми чертами
и именованными группами под это не подходит и остается данными.

## Текст в файлах ресурсов

Комментарий в `.css`, `.js`, `.html` и `.svg` – такая же фраза, как комментарий модуля. Раньше
такие файлы копировались байт в байт: русский текст попадал в английскую сборку без предупреждения, а `--strict`
считал файл покрытым, потому что считать там было нечего.

Перевод читает в них:

- комментарии `/* */` и `//` в `.css` и `.js`;
- комментарии `<!-- -->` в `.html` и `.svg`;
- текст `<title>` и `<desc>` в `.svg`: эти слова произносит экранный диктор, а браузер
  показывает их в подсказке;
- комментарии вложенных `<style>` и `<script>`.

Ключ фразы тот же, что у комментария модуля: маркер и обрамление сняты, блок разобран по строкам.
Одно предложение, написанное и в модуле, и в стилях, закрывается одной записью. Пробел находится
режимом `--gaps`, учитывается в покрытии и приводит к ошибке `--strict`.

Селекторы, имена свойств и их значения, атрибуты, идентификаторы и текст страницы остаются как
написаны. Файл читается разбором посимвольно, поэтому маркер внутри данных комментария не
открывает: `content: "/*"`, адрес в `url(...)` без кавычек, шаблонная строка, регулярное выражение
вида `/[/*]/`. Разметку разбирает html-парсер стандартной библиотеки – поэтому `<!--` в
значении атрибута не открывает комментарий.

Две границы проведены намеренно. Комментарий с лицензией остается как есть: его формулировка –
юридический текст, и перевод скажет не то, что сказал оригинал. Минифицированный `.css` или `.js`
пропускается целиком: это сборочный вывод, от комментариев в нем остается одна шапка, и править
там никто ничего не станет. Минифицированным считается файл, у которого самая длинная строка
длиннее пятисот символов.

## Записанное дерево – это репозиторий

`--out КАТАЛОГ` считает названный каталог корнем репозитория: проект ложится в
`КАТАЛОГ/{Поставщик}/{Имя}`, используя два имени из переведенного дескриптора.
Другой раскладки сборка не принимает: она пакует файлы по схеме `{поставщик}/{имя}` и каталог с
другим именем отвергает. Поэтому дерево выкатывается как есть, без ручной перекладки. Имена
берутся переведенные: проект, чье имя само по себе русское слово, меняет его при переводе, и
каталог следует за ним.

Каталог, который уже заканчивается этими двумя именами (`--out build/acme/tasks`), считается самим
каталогом проекта и второй раз не вкладывается. Путь, который писали руками, пока ключа не было,
продолжает работать. Дерево без дескриптора – фрагмент, переведенный отдельно – пишется туда, куда
попросили. Строка журнала называет каталог, в который файлы легли на самом деле.

Повторный запуск в тот же каталог просто переписывает дерево, а сам каталог узнается по
дескриптору `Project.yaml` или `Проект.yaml`. Каталог, занятый чужими файлами, не изменяется:
команда указывает этот каталог и дальнейшие действия. Отдельный файл, который записать не
удалось, называется в отчете вместе с причиной и проход не роняет. Мешает обычно остаток прошлого
запуска: каталог на месте файла, файл только для чтения, файл занят другой программой. Отчет
печатается целиком, первые пять таких файлов названы поименно, остальные сосчитаны. Запуск,
которому не удалось записать дерево, возвращает ненулевой код и без `--strict`: дерево – это и
есть его работа.

**`--clean`: остатки прошлого запуска.** Перезапись покрывает только те файлы, которые запуск
пишет, и больше ничего не трогает. Поэтому файл, переименованный или снятый в исходнике,
оставляет свое старое отражение в дереве вывода. Сборка берет каталог целиком, и сирота уезжает
вместе со всем остальным. Хуже того, остаток может стоять ровно на месте нужного файла: каталог
вместо файла – это и есть ошибка записи выше. `--clean` убирает перед записью все, чего этот
запуск не пишет:

```sh
xbsl translate e1c/app --out build --clean
```

Ключ задают явно, потому что он удаляет файлы. Записью во временный каталог с последующей
подменой это не заменить: подмена все равно обязана удалить старое дерево, стоит вторую полную
копию проекта и ломается ровно там же, где случаются ошибки записи, – на другом томе, на
каталоге, занятом сборкой. Отказ каталогу с чужими файлами остается страховкой сверху. Чистка
идет только внутри каталога, который уже является переведенным проектом, поэтому `--clean` не
превращается в "сотри то, на что показали". Неудавшееся удаление называется проблемой так же, как
неудавшаяся запись. Число убранного печатается в отчете и в поле `removed` у json только тогда,
когда убирать было что, а под числом перечисляется каждый остаток поименно: одно число не показывает, какие файлы исключены из сборки.

**`--dry-run`: посмотреть заранее.** Иначе первая чистка переведенного дерева делается вслепую.
Ключ доводит работу до записи и останавливает. Дерево построено, каталог назначения проверен –
занятый чужими файлами отвергается здесь так же, как отверг бы настоящий запуск, – остатки
перечислены. Записывать и удалять при этом нечего.

```sh
xbsl translate e1c/app --out build --clean --dry-run
```

```
Пробный запуск: ничего не записано и не убрано
будет записано файлов: 1261 -> build/Acme/TaskBook
будет убрано остатков прошлого запуска: 2
  Формы/СтараяФорма.yaml
  Основное/Ресурсы/percent.svg
```

Текстовый отчет называет первые двадцать и считает остальные. В json лежат `dry_run`, `planned`
(размер дерева, которое было бы записано) и `removals` – все до одного. Без `--out` описывать
нечего, и ключ отвергается, а не игнорируется.

Табличные режимы – `--gaps`, `--entries`, `--table`, `--unused`, `--redundant`, `--drift`,
`--suggest` –
не записывают дерево. Поэтому `--out`, `--clean`, `--dry-run` и `--missing` они тоже
отвергают и называют запуск, который дерево пишет.

## Словари локализации переворачиваются

Проект, у которого целевой язык уже лежит в секциях локализации, получает эти значения как
базовые, с переведенными ключами. Исходные значения уезжают в `Локализация/<Код>/`, а язык по
умолчанию и язык разработки в дескрипторе следуют за этим. Ключ, у которого значения на целевом
языке нет, сохраняет исходное и попадает в отчет.

С базой меняется местами только перевод на целевой язык. Его папка находится по коду языка
без учета регистра – так же, как ее находит 1С:Элемент. Перевод на любой другой язык
(`Локализация/Vi` рядом с `Локализация/En`) остается на своем месте: его ключи переводятся тем
же словарем, что и ключи базы, а значения остаются на своем языке. Английские названия языков
берутся из данных 1С:Элемента, поэтому описанию проекта с вьетнамским языком запись словаря для
него не нужна.

## Покрытие и пробелы

`--coverage` печатает долю словаря по каждому объекту метаданных – это семейство yaml и xbsl с
общей основой имени – и по проекту целиком. `--missing` пишет остаток заготовкой словаря: записи
идут по убыванию частоты, у каждой стоит число вхождений и первое место, а значения пустые и
готовы к заполнению.

Три счетчика разведены намеренно. Первый – покрытие словаря, число, которое команда доводит до
100%. Второй – пробелы данных 1С:Элемента, их записью в словаре не заклеивают. Третий –
кириллические скаляры, оставленные данными: их перечисляют, чтобы ревизор подтвердил, что это и
правда данные.

Словарь ищется рядом с проектом и выше. Корень без словаря отвергается с перечнем мест поиска, а
если словарь нашелся ниже корня, отказ называет и его. `--dictionary` называет словарь явно,
файлом или каталогом. `--target` называет файл, в который лягут новые записи; по умолчанию это
`090-manual.yaml`. Для каталога словаря передается только имя файла: путь с `/`, `\` или
буквой диска отвергается до записи любых правок. Та же проверка действует в MCP `translate_set`.
`--comment` задает заголовок, с которым такой файл создается: там и место
сказать, чему посвящена порция. `--format json` отдает весь отчет машине.
`--no-localization-swap` оставляет словари локализации как есть – это для проекта, который
переводит исходники, но раскладку языков менять не хочет.

`--strict` дает ненулевой выход, пока покрытие неполно или найдены проблемы. Это и нужно задаче
конвейера перед выкладкой переведенной сборки. Одна из таких проблем – столкновение имен. Два
разных имени одного пространства, переведенные в одно слово, ломают сборку, потому что компилятор
отвергает повтор имени. Увидеть это может только переводчик. Каждое столкнувшееся имя названо со
своим местом: `method:СтрокаРолей - 'Number' <- ... (Модуль.xbsl:2:9), ... (Модуль.xbsl:5:13)`.
Одно только имя пространства оставило бы читателю поиск двух слов среди полутора десятков,
объявленных методом, а рядом они стоят редко.

Встроенный тип, который метод читает корнем статического обращения, стоит в том же пространстве имен.
Локальная переменная, переведенная словом этого типа, закрывает тип в английском дереве, поэтому
пара называется с обоими местами, а запись, уточненная именем метода (`Метод.Имя`), разводит их.

Еще три проблемы приходят из самого словаря. Все три нашлись на живом проекте, английская сборка
которого не собиралась при покрытии 100%. Первая – запись, которая задает члену встроенного типа написание, отсутствующее в данных 1С:Элемента: `Важность: Severity` вместо `Importance` у события. О ней сообщают
в первом месте, где это доказывает приемник известного типа. Там используется написание из данных 1С:Элемента,
а приемник, тип которого никто не назвал, получит слово из записи, и компилятор его отвергнет.
В записи нужно указать написание из данных 1С:Элемента. Если в данных есть два написания, совпадение с любым из них не считается ошибкой: `Загрузить` – это `Load` у двоичного объекта и `Upload` у хранилища
объектов, и запись, совпадающая с любым из них, ничего не ломает. Вторая проблема – именованный
литерал, подстановки которого после перевода расходятся с подстановками ключа: `%{AccountCode}`
там, где поле переводится как `SubscriberCode`. О нем сообщают с обоими списками, потому что
имена внутри `%{...}` должны переводить те же поля на любом из двух языков.

Третья – тип, который проект объявляет под именем встроенного типа, и запись, переводящая его другим
словом. Выражение типа обычно берет встроенное имя поверх любого имени проекта, но тип, объявленный
проектом, – исключение: его объявление и его употребления обязаны двигаться вместе, поэтому запись
отвечает в каждом выражении типа с таким написанием, в том числе там, где стоит встроенный тип. Узел
пикера назывался `Образец`, запись `Образец: Swatch` превратила `новый Образец(...)` в файле, ничего
про пикер не знавшем, в `new Swatch(...)`, и сборка ответила `Type "Swatch" is not defined`. Никакое
значение это не лечит, и лечение – не значение: тип проекта надо переименовать. Запись, повторяющая
написание из данных 1С:Элемента, не изменяет встроенные имена и не проверяется.

Локализуемый текст yaml без пары в плане `literals` тоже приводит к ошибке `--strict` – всякое значение,
которое метамодель объявляет `Localizable`, кроме `Описание`: `Представление` где бы оно ни стояло,
заголовки приложения, сообщение запроса разрешения, представление группы справочника, два
представления переключаемой команды, шаблоны представления события журнала. Сборка такое дерево
примет, но на его страницах текст останется русским. Отчет перечисляет такие тексты с местами, а
строка вердикта называет их число. Текст, который должен остаться русским, называют записью,
повторяющей его значением (см. выше). Другие пропуски плана `literals` не приводят к ошибке проверки.

## Английский текст словаря

Покрытие показывает, есть ли перевод у каждого имени и каждой строки комментария, но не показывает,
читается ли перевод как английский текст. Механическая правка значений – замена, прогнанная по
тысячам строк, или волна, переписавшая русские ключи, – оставляет следы, которых `--strict` не
видит. Правило `translation/english-shape` – warning, включено по умолчанию, область файловая –
читает значения файлов словаря и сообщает о трех таких следах:

- окончание, приклеенное к слову, которое его не принимает: наречие, неправильное причастие или
  вспомогательный глагол, записанные как глагол или множественное число (`onlies`, `gones`,
  `hases`), и правильное причастие во множественном числе (`loadeds`);
- страдательный залог, сразу за которым идет именная группа без `by` ("a variable is shadowed the
  parameter"): подлежащее и дополнение остались на местах русской фразы;
- прописные, которых нет в русском ключе: "does NOT narrow" при ключе, где ничего не выделено.
  Выделенное слово в русском ключе их оправдывает, как и то же латинское слово в ключе. Аббревиатуры
  (`MB`, `URL`) и константы не проверяются.

Находка стоит на слове в файле словаря и приходит без исправления: выбрать нужное слово должен автор. Проверяются только файлы найденного словаря. Проект без словаря не получает таких находок, а
при проверке каталога с проектом и его `xbsl-translation` проверяются исходники и словарь вместе.

В VS Code находки видны и тогда, когда `xbsl.projectRoot` сужает проверки до папки проекта.
Расширение передает файлы словаря языковому серверу при наборе, а сервер добавляет словарь в
проверку всего проекта.

Словарь читают и два правила группы `comment/`: значение `phrases` – это английская строка
комментария. `comment/first-person` сообщает о "we", "our" или "I" в ней, а `comment/emphasis-caps` –
о прописных буквах для выделения: пришедших от выделенного ключа, о приставке капсом ("UNfilled") и об
артикле во фразе капсом. Прописные, которых нет в невыделенном ключе, остаются за
`translation/english-shape`, так что слово сообщается один раз. Литералы, токены и термины эти
правила не читают. Оба выключены по умолчанию и включаются ключом `--enable comment`.

## В редакторе

Правило `conventions/missing-translation` – info, выключено по умолчанию, область проектная –
показывает те же пробелы на их местах. Имя или строка комментария, которых нет в словаре, дают
одну находку на первое вхождение в файле. Пока словарь не найден, правило не выдает находок, поэтому работает
только в проекте с переводом исходников. Включает его
`--enable conventions/missing-translation`, а в редакторе – настройка Linter: Enable.

Замечание содержит ключ словаря, его вид и подсказку. Меню быстрых исправлений позволяет записать перевод, не выходя из файла. "Перевести как ..." записывает предложенное написание 1С:Элемента одним щелчком.
"Перевести ..." спрашивает слово. Третье действие открывает таблицу словаря с отбором по этому
ключу. После записи проект проверяется заново, перезапускать ничего не нужно.

**Таблица словаря** открывается командой "XBSL: словарь перевода" и показывает записи рядом с
тем, что исходники еще не покрывают: вид, ключ, перевод, число вхождений, первое место и файл
словаря. Каждая запись занимает две строки, а поле перевода растянуто под остальным во всю ширину
строки. Поле правится на месте. Строка поиска и переключатель "только незаполненные" сужают
таблицу. Подсказка – сперва написание из данных 1С:Элемента, иначе догадка внешнего сервиса – стоит серым
внутри пустого поля и подставляется щелчком или клавишей `Enter`. Таблица читает `--table`,
который за один проход по проекту отдает записи, пропуски и покрытие, а пишет она ключом `--set`.
После записи ячейки проект заново не обходится: перечитывается только словарь, а счетчики шапки
сдвигаются на то, что изменила эта правка. Точные числа возвращает кнопка "Перечитать".
Кнопка "Запросить машинный перевод" в этой же панели заполняет пустые поля
предложениями внешнего сервиса, подробности – в разделе
[Машинный перевод](#машинный-перевод) ниже.

## Наполнение словаря из инструментов

Словарь большого проекта может содержать тысячи записей. Для просмотра и изменения доступна постраничная работа через общее ядро движка.

**CLI** отвечает на те же вопросы, что задает панель:

```sh
xbsl translate e1c/app --gaps --kind token --limit 20      # чего не хватает, по убыванию частоты
xbsl translate e1c/app --entries --filter Задач            # что словарь уже говорит
xbsl translate e1c/app --table --limit 0                   # всё сразу: записи, пропуски, сводка
xbsl translate e1c/app --set правки.yaml                   # применить пачку из файла (ниже)
xbsl translate e1c/app --unused                            # пары, которых проект уже не использует
xbsl translate e1c/app --stale --filter ПодсказкаТарифа     # то же об именах одного удалённого компонента
xbsl translate e1c/app --redundant                         # пары, на которые платформа отвечает сама
xbsl translate e1c/app --drift                             # фразы, где имя названо не по паре
```

`--table` отвечает на три вопроса разом, одним проходом. Эти данные используются в таблице редактора. Порознь это два одинаковых обхода исходников в двух процессах и
третье чтение того же словаря.

`--set` принимает пачку файлом в любом из двух форматов. Первый – yaml самого словаря: секции
`tokens`, `phrases` и `literals`, то же квотирование, что в файлах словаря, а пустое значение
снимает запись. Второй – список JSON `[{key, value, kind}]`, который отдают скрипты. Пачка на
сотни записей пишется так же, как сам словарь, а не одной строкой JSON в команде. Yaml читает
загрузчик самого словаря, поэтому пачка, которую скрипт выгрузил с ключами в кавычках
(`yaml.safe_dump(..., default_style='"')`), читается так же, как написанная вручную. Пачку без
записей команда отвергает и называет ключи верхнего уровня, которые в файле есть.

При записи словаря выводятся предупреждения о двух видах пар, которые можно обнаружить без
проверки проекта. Первая пара содержит значение, уже занятое другим ключом того же пространства
имен. Вторая содержит ключ, совпадающий с именем 1С:Элемента. Если ключ совпадает с именем
типа, может потребоваться переименование узла проекта. Если он совпадает с именем члена типа,
нужно использовать написание из данных 1С:Элемента (`ЦветСсылок: LinksColor` при
`DesignTheme.LinksColor`).

Оба случая при записи пары приводят к предупреждению. Строгая проверка проекта обнаруживает
ошибку, если проект объявляет собственный тип с именем встроенного типа, а запись задает ему
другое написание. Ключ с владельцем
(`<Владелец>.<Имя>`) действует в одном пространстве имен, не используется в выражениях типа и не
проверяется на это совпадение. `translate_set` возвращает эти данные в `collisions` и
`platform_names`, а `--set` выводит их в stderr рядом с числом записей.

В отличие от `--gaps`, который показывает недостающие переводы, `--unused` выводит записи
словаря, которые больше не используются в проекте, например имена и
строки комментариев удаленного кода. `--strict` проверяет непереведенные места, а `--entries`
показывает объявления записей без проверки их использования. `--prune` удаляет перечисленные
записи с учетом ограничений `--kind`, `--filter` и выбранной страницы. Если `--limit` сокращает
список, отчет указывает на это: удаляются только записи показанной страницы.

`--stale` является другим именем того же режима. Фильтр `--filter` позволяет ограничить список,
например именами удаленного компонента.

`--unused --since` ограничивает список записями одной правки. В него входят ключи, которые больше не
используются в проекте и встречались только в строках, удаленных этой правкой, а также пары,
добавленные или измененные этой правкой в словаре. С `--prune` удаляются перечисленные записи.

Для ветки или коммита сравнение выполняется от точки расхождения с HEAD до рабочего дерева,
поэтому учитываются и незакоммиченные изменения. Диапазон `A..B` передается Git как указан.
При проверке одного проекта без отбора было найдено 3297 неиспользуемых записей, из них к правке
относились 18: девять имен и девять строк комментариев. Для их поиска потребовался один вызов
вместо девятнадцати вызовов с `--filter` по одному имени.

Кандидаты определяются по удаленным строкам исходников и по добавленным или измененным парам в
диффе файлов словаря. Например, строка комментария, добавленная и измененная в одной ветке, может отсутствовать в
диффе с базой как удаленная строка. Пара первого варианта также находится по диффу словаря.
Каждая запись сверяется с рабочим деревом; в список попадают только ключи,
которые в нем не используются. Заголовок и блок `since` в `--format json` содержат число файлов
правки, файлов словаря в ее диффе и пар на добавленных строках.

Удаленные строки получаются из `git diff`. Комментарии разбираются в старой версии файла из Git,
поэтому учитываются и неизмененные границы блока. Относительные пути проекта и словаря отсчитываются
от каталога запуска. Если Git не ответил за минуту, команда завершится с ошибкой и предложит
ограничить список без Git с помощью `--filter`.

Обход исходников печатает прогресс в stderr каждые 200 файлов, чтобы долгий запуск было видно;
stdout остается отчетом, и `--format json` там – один документ. В этом виде каждая строка `unused` содержит `kind`, `key`, `value`, `file`, `line` и `scope` – их и читает скрипт вместо разбора текстовых
строк по двойным пробелам, которые ключ может содержать и сам.

Сужение работает как пересечение, а не как короткий путь: имя, которое проект все еще пишет,
сиротой не станет, как бы щедро ни прочитался diff. Поэтому ответ без отбора и без `--since`
содержит предупреждение. Проверка текстовая; список описывает весь накопленный словарь и предназначен для просмотра, а не для полного удаления записей.

Чтение текстовое, и важно, в какую сторону оно ошибается. Имя, которое встречается еще и в
прозе, может быть сочтено используемым, и тогда пара просто останется на месте. Живую пару
сиротой при этом не назовут. Строка комментария читается разбором самого переводчика: маркер и
обрамление снимаются ровно так же, как их снимает записывающий проход. Ключ литерала тоже берется
так, как его берет проход. Файл yaml проходит обход самого переводчика, а тот отличает
представление и шаблон от имени. Модуль разбирает лексер, поэтому строку внутри интерполяции
другой строки он видит целиком. Имя ищут и в именах
файлов, потому что папка и файл проходят через ту же плоскость имен. Квалифицированный ключ
`<Владелец>.<Имя>` проверяется по обеим частям: в исходниках они написаны порознь, и чтение текста с
точкой как одного имени объявило бы сиротой каждую такую пару.

`--redundant` показывает пары словаря, которые повторяют написания из данных 1С:Элемента.
Без таких пар результат перевода остается тем же. Эти записи могут скрывать пробелы данных или
движка. Например, в одном словаре пары для языков описания проекта скрывали неполный перевод
перечисления; его обнаружил тест с пустым словарем. Обычный отчет показывает число таких пар,
а `--prune` удаляет перечисленные записи.

В отличие от `--unused`, команда выполняет полную проверку проекта. Пара считается лишней,
только если без нее результат остается тем же во всех местах ее использования. Если пара нужна
хотя бы в одном месте, она сохраняется: например, когда в данных технологии есть написание для
одной роли слова, но нет для другой. Пары, которые проект не использует, проверяет `--unused`.

`--drift` смотрит на фразы. Строку комментария словарь переводит целиком, вместе с именами, и
ничто не связывает имя внутри перевода с разделом токенов. Токен переименовали после того, как
фразу написали, или строку перевели со своим представлением об имени, – и английский комментарий
называет то, чего в английском дереве нет. Раньше это оставляло один след: находку
`comment/unknown-name` на английском дереве, у комментария, а не у записи, которую надо поправить.
Режим перечисляет каждое имя из ключа фразы, у которого есть пара – токен проекта или английское
написание 1С:Элемента, – если перевод не содержит ни одного написания пары и называет вместо него
что-то неизвестное: `ОбщееСклада -> StockCommon, а перевод называет WarehouseCommon`, с файлом и
строкой записи. Перевод, который передает имя простыми словами, ничего не называет, и в список не
попадает. Пару, написанную на всю строку тега, режим проверяет еще и по имени после тега, какой бы
формы оно ни было (параметр, названный одним простым словом, – все равно имя сигнатуры), и по
слову тега: `@возвращает -> @returns, а перевод называет @return`. Режим читает только словарь,
отвечает за секунды и в `--strict` не входит: дерево
собирается в любом случае, а проверка определяет, соберется ли оно. Обычный отчет
перевода считает такие фразы одной строкой со ссылкой на `--drift`, когда они есть (в json – поле
`dictionary_drift`); код выхода от них не меняется.

`--gaps` показывает частоту, первые места употребления и `suggestion` – написание из данных 1С:Элемента, если оно там есть. Подсказка остается подсказкой: имя, объявленное проектом, может
намеренно требовать другого слова. Внутреннее имя 1С:Элемента – класс метаданных вроде `CodeAttrMd` –
не предлагается.

**Инструменты MCP** – те же шесть, для агента, который наполняет словарь:

- `translate_status` – покрытие и остаток, дешевая проверка перед любым решением; `against` называет
  git-ссылку и добавляет отчет `--check-duplicates` о коллизиях с ней, где дубли, которые
  есть и на ссылке, только посчитаны (весь список дает `full`); `drift` считает фразы, которые
  перечисляет `translate_drift`;
- `translate_gaps` – непереведенное страницами (`kind`, `filter`, `limit`, `offset`), в ответе –
  прочитанный `dictionary`;
  `compact` отдает по строке только `{key, kind, count}` – форму рабочего списка
  переводчика, когда полные строки не влезают в ответ;
- `translate_entries` – что уже в словаре, с файлом и строкой каждой записи, чтобы новое слово
  согласовывалось с принятыми; по умолчанию десять строк, а `compact` оставляет по строке
  `{key, kind, value}` – ответ на вопрос "как переведен термин" без мест, которые давали десять
  килобайт на вызов по частому корню;
- `translate_unused` – записи словаря, которые больше не используются в проекте; `filter`
  сужает ответ до имен одного удаленного компонента – или сразу до списка подстрок, и тогда ответ
  называет в `unmatched` те, под которые не попала ни одна сирота; `since` – до сирот одной правки
  (ветка, коммит или диапазон `A..B`): ключи на снятых ею строках и пары, которые она добавила в
  словарь, обе стороны сочтены в блоке `since`; `prune` (по умолчанию выключен) снимает все ключи,
  которые выбрали отборы, какой бы ни была страница, вместе со всеми их объявлениями. После снятия
  список по умолчанию не возвращается: `removed` считает вхождения, `pruned.keys` – пары,
  `pruned.by_kind` / `pruned.by_file` дают разбивку; `compact=false`
  возвращает полные строки. Просмотр остается полным по умолчанию, а `compact=true` оставляет
  ключ, вид, файл и строку. `counts` считает всех отфильтрованных кандидатов по видам; `budget_seconds` (по умолчанию 300) ограничивает обход
  исходников – по истечении ответ состоит из прочитанного, помечен `partial` и содержит `sources` с числом прочитанных и общим числом файлов, а также `note` о продолжении. Такой ответ содержит только кандидатов: `prune` ничего не удаляет; ответ без `filter` и `since` содержит `note` о стоимости чтения;
- `translate_redundant` – пары, для которых данные 1С:Элемента дают то же написание и без которых проход
  написал бы то же слово: обходы, прячущие пробел данных 1С:Элемента или движка. `filter`
  сужает ответ, `prune` (по умолчанию выключен) снимает все пары, которые выбрал `filter`, какой
  бы ни была страница, и `pruned.keys` их считает; в отличие от `translate_unused` он делает полный проход – вердикт держится на
  местах, где запись действительно отвечала;
- `translate_drift` – фразы, чей перевод называет имя не так, как его пара (список `--drift`):
  в строке имя, написания пары, имена, которые перевод называет вместо них, и файл со строкой
  записи; `filter` сужает ответ по любому из этих текстов;
- `translate_set` – запись: добавить, исправить на месте или снять, обнулив значение;
  `edits_file` – пачка файлом в тех же двух форматах, что читает `--set`.

Ответ с неполной страницей содержит сведения об оставшихся записях. `total: 72` рядом с ровно пятьюдесятью строками
выглядит полным ответом, и однажды словарь, собранный по такой странице, оказался короче на
двадцать две записи. Нашел их строгий проход уже после слияния. Поэтому неполная страница содержит
`truncated: true`, `remaining` и `hint` со следующим `offset`. Весь список отдает `limit=0`, а у
пропусков есть еще `--missing`, который записывает весь остаток файлом заготовки словаря.

Новая запись попадает в `090-manual.yaml` (или в файл из `target`), а уже существующая
изменяется во всех местах, где словарь объявляет этот ключ. Пустое значение
снимает все копии, а какую копию убрать, решает человек: так их перечисляет `--check-duplicates`.
Новые дубли при записи не создаются. Ключ, переведенный по-разному в двух местах – в
двух файлах или дважды в одном, – словарь отвергает при загрузке, а `--check-duplicates` перечисляет
все такие ключи, не загружая словарь.

## Машинный перевод

Заполнить большой остаток вручную долго, и `--suggest` берет недостающее из внешнего
переводческого сервиса. Возвращается оно предложениями, а не записью: словарь не меняется, пока
предложение не принято. В консоли его принимает флаг `--suggest-out`, в редакторе – щелчок или
клавиша `Enter` по подсказке в таблице.

```sh
xbsl translate e1c/app --suggest                                  # отчёт: что предложил сервис
xbsl translate e1c/app --suggest --provider yandex                # выбор сервиса явно
xbsl translate e1c/app --suggest --suggest-out 080-machine.yaml   # записать план рядом со словарём
xbsl translate e1c/app --suggest --plans tokens                   # добивать только имена
```

Идет такой запуск всегда по всему проекту. Ограничить его нечем, остановить на полпути нельзя,
заранее оценить объем тоже нечем. При этом каждая отправленная порция – платный запрос к
сервису.

`--suggest-out` называет файл плана, в который лягут предложенные записи. Каталог из пути
отбрасывается, берется только имя файла, и оно ложится внутрь каталога словаря. Если словарь –
это один файл, отдельного плана не выходит: записи ложатся в него же.

Без `--provider` движок берет единственный настроенный сервис. Если не настроен ни один, отказ
называет переменные окружения, которых не хватает. Если настроено больше одного, отказ
перечисляет сервисы `google` и `yandex` и предлагает выбрать один флагом `--provider`.

**Два сервиса, и они не взаимозаменяемы.**

- **Yandex Translate** – авторизация ключом сервисного аккаунта и идентификатором каталога
  (folder), нужны оба. Порция – до 10000 символов за запрос. Глоссарий поддерживается: список
  терминов проекта уходит вместе с текстом самого запроса.
- **Google Translate** – авторизация одним ключом, порция до 5000 символов. API глоссарий не поддерживает, поэтому написание термина накладывается уже после ответа, когда движок собирает имя
  из вернувшейся прозы.

Сколько бы ни позволял сервис, в одном запросе едет не больше 100 текстов. Это собственный
предел движка, взятый с запасом. Порция, отвергнутая целиком за размер, стоит ровно столько же,
сколько принятая, а ограничение только по общей длине позволило бы отправить в одном запросе шестьсот однословных имен.

**Ключи – в окружении, никогда в командной строке или в файле настроек.** Три переменные,
поименные под каждый сервис:

- `XBSL_TRANSLATE_YANDEX_KEY`, `XBSL_TRANSLATE_YANDEX_FOLDER` – ключ и каталог Yandex, нужны
  оба;
- `XBSL_TRANSLATE_GOOGLE_KEY` – ключ Google, один.

В редакторе переменные окружения заводить не нужно: команда **XBSL: Задать ключ машинного
перевода** (`xbsl.translate.setKey`) предлагает выбрать одно из трех значений и сохраняет его в защищенное хранилище (SecretStorage) расширения – оно передает его движку в окружении самого
запуска `--suggest`, а не в настройке и не в командной строке. Настройка
`xbsl.translation.provider` выбирает сервис, если настроены оба сразу; сам ключ ею не задается.

**Кэш** лежит в файле `machine-cache.json` рядом со словарем: в каталоге `xbsl-translation`,
если словарь – каталог, иначе рядом с единственным файлом словаря. В нем хранится сырой ответ
сервиса по ключу из четырех частей: сервис, язык, отпечаток глоссария, текст. Готовое имя там не
хранят: правила сборки имени и список терминов могут измениться, а повторный запрос того же текста не требуется. Формат JSON выбран не случайно: словарь ищет `*.yaml` рекурсивно и принял бы
файл кэша за еще один план перевода с повторяющимися ключами. Запись остается в кэше независимо
от того, приняли предложение в словарь или нет. Повторный `--suggest` не платит за один и тот же
текст дважды, даже если прошлый ответ никто не принял.

**Секция `terms` словаря** – это короткий список "русский термин -> английское написание".
Планом перевода она не является и в покрытие не входит. Из нее берут сразу две вещи: пары
глоссария, которые уходят в запрос вместе с текстом (эту возможность поддерживает только Yandex), и написание для
сборки имени. Вторая половина работает уже по ответу сервиса. Собирая идентификатор, движок
сверяет каждое английское слово ответа со списком терминов без учета регистра и ставит словарное
написание, где бы слово ни стояло во фразе. Русские формы слова при этом не разбираются.
Термин, вернувшийся другим английским словом – множественным числом, синонимом, – не опознается и
остается таким, каким его прислал сервис. На перевод строки комментария (`phrases`) термины не
влияют: комментарий целиком остается тем, что ответил сервис.

**Имена собирает движок, а не сервис, и собирает по одним и тем же правилам.** Сервис отвечает
прозой, например "Site address", а плану `tokens` нужен идентификатор. Движок убирает служебные
слова (a, the, of...), подставляет написание термина, где оно есть, и склеивает остаток, начиная
каждое слово с большой буквы. Имя, уже занятое другим ключом словаря, `--suggest` отклоняет с
названной причиной. Так же он поступает с прозой, из которой не вышло собрать идентификатор.
Угадывать и переписывать поверх он не станет.

**Литералы не отправляются в сеть.** `--suggest` посылает сервису только пробелы `tokens` и
`phrases`, то есть имена и строки комментариев целиком. Строковый литерал заполняется отдельно и
только тогда, когда его текст целиком совпадает с уже принятым именем. Делается это локально, без
единого запроса к сервису.

**Что уходит наружу.** Сервис получает только текст пробела: имя так, как оно написано в
проекте, или строку комментария целиком. Ни путь файла, ни код вокруг, ни остальной проект сервис
не видит. Без ключа команда не делает ни одного запроса ни к Yandex, ни к Google: она сразу
отказывает и называет переменную, которой не хватает.

Итог печатается тем же способом, что и у `--set`. `cached` – сколько ответов взято из кэша,
`requested` – сколько запрошено заново, `refused` – сколько отклонено, и у каждого отклоненного
названа причина.

В редакторе те же три числа остаются в собственной строке сводки панели до следующего запуска.
Раньше эти числа отображались только в сообщении строки состояния, которое исчезает через несколько секунд.
При наведении на эту строку отображается причина каждого отказа. Когда непереведенного текста не было, и запрашивать было не о
чем, в строке выводится сообщение вместо трех нулей. Когда все предложения дали локальные
совпадения литералов без единого запроса, сказано и это.

### Ссылки в выражениях динамического списка

В источнике динамического списка `Строки.Ссылка` переводится как `Reference`, если
`Строки` – явно заданный псевдоним основной или присоединенной таблицы. Это относится
к свойствам с выражениями внутри того же источника, включая отборы. Другие приемники
и свойства-ссылки элементов интерфейса сохраняют обычное прочтение. Локальная запись
словаря проекта может переопределить написание ссылки.
