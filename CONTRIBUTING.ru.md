# Как дорабатывать xbsl

[English](CONTRIBUTING.md) · **Русский**

Спасибо за вклад. Ниже собран минимум, которого хватит, чтобы добавить правило или обновить
данные.

## Окружение

Требуется Python 3.10 или новее. Данные о языке в репозиторий не входят, поэтому сначала
сгенерируйте их из своего дистрибутива 1С:Элемент. Без них не заработают ни линтер, ни часть
тестов:

```sh
python tools/extract.py --dist "<каталог дистрибутива>"     # все наборы данных

pip install -e ".[dev]"     # линтер + pytest + PyYAML
pytest                      # тесты (без данных зависящие от них пропускаются)
python -m xbsl <путь>   # проверка исходников
```

### Проверка в редакторе до релиза

Чтобы увидеть правку движка вживую, переустанавливать пакет не нужно. Настройка
`xbsl.lsp.command` указывает на `tools/lsp-dev.cmd`, и обёртка запускает LSP-сервер из этого
клона. PYTHONPATH идёт раньше site-packages, поэтому клон побеждает установленный пакет из
любого каталога. После правки настройки перезагрузите окно: строка состояния покажет версию
движка из клона. Чтобы вернуться к установленному пакету, уберите настройку и перезагрузите окно
снова. Интерпретатору нужны дополнительные наборы `[lsp]` и `[morph]`.

Подкоманды CLI из клона запускаются иначе. `python -m xbsl` разбирает только режим проверки:
подкоманду он примет за путь и проверит 0 файлов. Пишите
`python -c "from xbsl.cli import main; main()" list-rules`.

### Какой именно xbsl сейчас работает

`python -m xbsl` из каталога клона кладёт рабочий каталог первым в `sys.path`, и исходники молча
подменяют установленный пакет. Проба тогда то падает, то нет – смотря откуда её запустили, – а
дефект выглядит плавающим. Поэтому проверяйте явно, какой модуль работает:

```sh
python -c "import xbsl.lexer as L; print(L.__file__)"
```

### Запуск процесса

Каждый вызов, который читает процесс как текст, называет `encoding="utf-8"`. Дочернему процессу
Python, запущенному отсюда, задаётся `PYTHONIOENCODING=utf-8`. Оба требования обязательны. На
Windows дочерний процесс пишет в кодировке консоли, здесь это cp1251, а родитель декодирует
utf-8. Поток чтения `subprocess` падает внутри себя, `stdout` возвращается `None`, и код возврата
при этом остаётся нулевым. В выводе ничто не намекает, что текст потерян. Так теряется русская
половина страницы документации, текста справки или трассировки с кириллицей в пути. Репозиторий
держит на этом `tests/test_conventions.py`, разбирая исходники через `ast`. Сам разбор живёт в
общем пакете `docsguard`: та же беда ждёт три репозитория. CI ставит этот сторож по тегу, чтобы
здешний вердикт не менялся без здешнего коммита.

## Как добавить правило

1. Создайте модуль в `xbsl/rules/` (или дополните существующий).
2. Объявите функцию-правило и повесьте декоратор:

   ```python
   from xbsl.diagnostics import Diagnostic, Severity
   from xbsl.engine import SourceFile, rule

   @rule("группа/имя", "Короткий заголовок", "B", severity=Severity.WARNING)
   def моё_правило(source: SourceFile):
       if source.kind != "xbsl":
           return
       # ... вернуть/выдать Diagnostic(path, line, col, rule_id, severity, message)
   ```

   - `тир`: `A` структура/YAML, `B` текст/конвенции, `C` код, `D` семантика.
   - `scope="project"` – для кросс-файловых правил; тогда функция принимает `list[SourceFile]`.
   - `enabled_by_default=False` – если правило шумит на старом коде (включается через `--select`).
   - Позиции строка/колонка – 1-индексированные. Для позиций используйте `xbsl.lexer.linemap`.

3. Подключите модуль в `xbsl/rules/__init__.py` (импорт регистрирует правило).
4. **Главное правило проекта:** запустите его на исходниках реального проекта и добейтесь **нуля
   ложных срабатываний**. Если правило массово срабатывает на существующем коде, сделайте его
   `info` и выключенным по умолчанию. Заставлять всех править старый код не надо.
5. Добавьте тест в `tests/` (образцы – в `tests/test_rules.py`).
6. Обновите сопутствующие метаданные тем же изменением: строку в таблицах `docs/RULES.md` и
   `docs/RULES.ru.md` (id, severity, умолчание, область, однострочное описание, ссылка на
   доки), счётчик правил там же и в обоих README, запись в
   `editors/vscode/src/ruleDocs.ts` – если за правилом стоит раздел документации платформы,
   счётчики уровней в описаниях групп (`editors/vscode/package.nls.json` и `.ru.json`), а для
   новой группы – ещё и настройку `xbsl.groups.<группа>` в `editors/vscode/package.json`.
   Всё перечисленное сверяется с реестром в `tests/test_metadata_sync.py`, так что забытое
   место видно сразу, а не при выпуске расширения.
7. **Если правило проверяет имя, заведите ему посев паритета** – см. ниже.

Лексер и данные о языке и типах извлечены из самой платформы: из грамматики Xtext и ANTLR и из
документации дистрибутива. Держитесь того же принципа и сверяйтесь с первоисточником.

### Паритет двух написаний: каждому правилу свой посев

Идентификаторы Элемента двуязычны, а таблицы, по которым судят правила, извлечены из
документации, которая существует только по-русски. Правило, сверяющее текст исходника с такой
таблицей, читает переведённый проект по словарю, в котором этого проекта нет. Оно пропускает
настоящие дефекты либо сообщает о том, что компилятор принимает. Лечится это выводом английского
написания из словарей платформы – `xbsl/terms.py` и `xbsl/uischema.py`. Написать второе написание
руками не поможет: догадка молча не совпадёт ни с чем.

Замер линтом по переведённому проекту со сверкой счётчиков находит только те правила, у которых
счёт сдвинулся. Правило, которое молчит на обеих сторонах, такой замер не видит – всё равно,
сломано оно или в проекте просто нет такой конструкции. Поэтому проверка сеет свой случай
сама:

```
python tools/parity_seed.py                    # все посевы
python tools/parity_seed.py --rule группа/имя  # одно правило
python tools/parity_seed.py --uncovered        # правила, за которые не отвечает ни один посев
```

Посев – это маленькое русское дерево и вердикт, который правило ему должно: находка или тишина.
Английский близнец берётся из собственного переводчика инструментария, а не из второй заготовки.
Так под проверку попадает то самое написание, которое инструментарий действительно порождает. В
вердикте названа ошибшаяся сторона и её промах: `en-misses`, `en-invents` и то же самое с
приставкой `ru-`. Таблица без английского написания заставляет правило пропускать, а без
русского прочтения – выдумывать, и лечится это по-разному. Посев, переставший сеять свой случай,
помечается как `stale`, молча он не пройдёт. Весь каталог запускает `tests/test_parity_seed.py`,
так что посевы проверяются при каждом запуске тестов, а не только когда об инструменте
вспомнили.

Дыру, которую сегодня не закрыть, всё равно стоит посеять. Укажите посеву причину через
`known=`, и вместо провала он даст `known (...)`. Удалить посев значило бы удалить
свидетельство, и следующий читатель открыл бы то же самое заново. Прятать за отметкой поломку
не выйдет: как только такой посев начнёт сходиться, он даст `fixed!` и уронит проверку. Это и
есть знак, что отметку пора снять.

## Данные под новую версию Элемента

Данные версионированы в `xbsl/data/element/<версия>/`. Чтобы добавить новую версию, возьмите её
дистрибутив и запустите экстракторы. Версию они определят сами:

```sh
python tools/extract.py --dist "<каталог дистрибутива>"     # все наборы данных
```

Файлы самого дистрибутива в репозиторий не коммитятся, их кэш лежит в `.refs/`. Коммитятся
только производные JSON.
